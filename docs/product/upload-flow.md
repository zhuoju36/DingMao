## 六、API 设计（✅ 已实现，2026-09-18）

| 端点 | 方法 | 用途 | 实现状态 |
|---|---|---|---|
| `/api/v1/projects/:id/documents` | GET | 列项目档案 | ✅ P0-7-A |
| `/api/v1/projects/:id/documents` | POST | 上传文件（multipart/form-data）| ✅ P0-7-A + 自动入队解析 |
| `/api/v1/projects/:id/documents/:doc_id` | GET | 详情（含 `parsed_content`）| ✅ P0-7-A |
| `/api/v1/projects/:id/documents/:doc_id` | DELETE | 删除（DB + 源文件 + 解析产物）| ✅ P0-7-B |
| `/api/v1/projects/:id/documents/:doc_id/reparse` | POST | 重解析（清产物 → 重置 pending → 入队）| ✅ P0-7-B |

实现位置：`backend/app/api/v1/documents.py`

### 6.1 POST 字段

```
file:           binary  （必填，PDF/图片，最大 50MB）
document_type:  enum    （必填，6 选 1）
title:          string  （可选，默认取原文件名）
```

### 6.2 后端流程（✅ 已实现）

```
1. POST /documents                        [app/api/v1/documents.py]
   - 鉴权：项目 owner（MVP 单用户；成员权限待 V2 ProjectMember）
   - 校验文件大小（>50MB → 422 DocumentValidationError）
   - 落本地 storage/projects/{project_id}/{doc_id}{ext}
   - 写 project_documents（parse_status=pending）
   - task_queue.enqueue_parse_document()  ← best-effort，队列挂了也返回 201
   - 返回 201 + document_id

2. ARQ worker（独立进程）                  [app/worker.py]
   - 启动: cd backend && .venv/bin/arq app.worker.WorkerSettings
   - 置 parsing → 调 ingest.parse_document()（subprocess 跑 MinerU）
   - 成功: parsed   + parsed_content + 产物落盘 storage/parsed/{pid}/{did}/
   - 失败: failed_parse + parse_error（不抛异常，避免 ARQ 无意义重试）
   - 文档在排队期间被删 → 静默跳过

3. POST /documents/:doc_id/reparse
   - 清 parsed_content / parse_error → 重置 pending → 重新入队
   - 去重：_job_id="parse:{doc_id}" + keep_result=0
     （去重窗口 = 排队中+执行中；任务结束后可再次重解析）

4. DELETE /documents/:doc_id
   - 删源文件 + 删解析产物目录 + 删 DB 行，返回 204
```

### 6.3 parsed_content 结构（实现与设计稿的偏差，已确认）

设计稿原写 `{markdown, middle_json}` 全内联。**实际实现只内联 markdown**：

```json
{
  "markdown": "……正文……",
  "page_count": 3,
  "markdown_chars": 253,
  "middle_json_bytes": 3958,
  "images": 0,
  "elapsed_sec": 3.2,
  "tier": "flash",
  "parsed_dir": "parsed/7/2"
}
```

**理由**：`middle.json` 单文件可达数百 KB（GB55037 实测 388 KB），逐份内联进 JSONB
会明显膨胀 DB；而 MVP 喂 LLM 只需要 markdown。完整产物（middle.json / images/ /
structured_content.json / model_output.json）留在 `storage/parsed/{pid}/{did}/`，
需要按页定位时再读盘。符合"原则 7 知识库与代码解耦（可重建）"。

### 6.4 MinerU 调用方式（关键架构约束）

MinerU 依赖 **7.3 GB**（torch/onnxruntime + 模型），不装进 backend venv（737 MB）。
后端通过 **subprocess** 调用「装了 MinerU 的解释器」执行
`backend/scripts/mineru_parse.py`，解释器路径由 `MINERU_PYTHON` 配置。

- 本地开发：`MINERU_PYTHON=../experiments/mineru-test/.venv/bin/python`
- 生产部署：需单独准备 mineru venv，填绝对路径（见 `.env.example`）
- 未配置时：上传仍成功，解析以 `failed_parse` + 明确错误信息失败（不静默跳过）

```
   │                                  │
   │         [取消]  [开始上传]        │
   └──────────────────────────────────┘
        │
        ▼
③ 上传中（按钮 loading）→ 成功
   · 关闭对话框
   · 列表顶部**立即**插入 pending 行（不等解析）
   · ElMessage："已上传，正在解析…"
   · 自动开始轮询（见 7.3）
```

**关键决策**：

| # | 决策 | 理由 |
|---|---|---|
| 1 | 拖拽区与"点击选择"共用同一路径（选完都开对话框） | 拖拽直传会让"类型必填"无处安放 |
| 2 | 类型在对话框选，不用拖拽区预选 | 单一交互路径，少一个状态 |
| 3 | 标题默认文件名去扩展名 | 减少输入；可改 |
| 4 | **单文件**（`:limit="1"`）| 后端 `POST` 是单文件接口，且每文件要选类型；多文件留 V2 |
| 5 | 对话框有明确"取消" | ia.md 原则 3（明确回退路径） |
| 6 | 上传成功**不等解析** | 解析 3s~数分钟；后端已是异步（P0-7-B） |

**放弃的方案**：

- ❌ **拖拽即上传**（类型用默认值，事后改）：后端无 `PATCH` 端点，改类型要加接口；且用户常忘记改 → 数据脏
- ❌ **多文件批量**：每文件需独立类型，对话框会变成表格，复杂度陡增（原则 2）

### 7.3 状态可见与自动刷新（ia.md 原则 5）

| 状态 | 徽章 | 副文本 | 行内操作 |
|---|---|---|---|
| `pending` | ⏳ 待解析（info）| "排队中…" | 下载原文 / 删除 |
| `parsing` | 🔄 解析中（warning）| "已进行 N 秒（大文件通常 1–3 分钟）" | 下载原文 / ~~删除~~（禁用）|
| `parsed` | ✅ 已解析（success）| "32 页 · 1.8 万字 · 耗时 47s" | 查看解析 / 下载原文 / 重新解析 / 删除 |
| `failed_parse` | ⚠️ 解析失败（danger）| "原因：{parse_error 截断 80 字}" | 下载原文 / 重新解析 / 删除 |
| `failed_upload` | ❌ 上传失败（danger）| — | **不会出现在列表**（上传失败在 HTTP 层报错，不落库）|
| `archived` | 📦 已归档（info）| — | V2 |

**轮询规则**：

```
列表加载后：若存在 pending/parsing 行 → 启动 setInterval(3000)
每轮：GET /projects/{id}/documents（列表接口，一次拿全部）
      若全部进入终态 → clearInterval
组件卸载（onUnmounted）→ clearInterval（防内存泄漏）
```

**决策**：

| 决策 | 理由 |
|---|---|
| 用**列表接口**轮询而非逐个详情 | 一次请求刷新所有行，简单且请求数少 |
| 间隔 3s | 解析 3~135s，3s 粒度足够感知；再密是浪费 |
| `parsing` 行禁止删除/重解析 | 避免与 worker 抢同一个文件（竞态）。后端也没做锁 |
| **不显示进度条** | 后端无真实进度。显示"已进行 N 秒"是诚实的信息 |
| 页面隐藏时暂停轮询 | **MVP 不做**，留 V2（省电/省流量） |

`parsing` 耗时来源：`now - updated_at`（worker 置 parsing 时刷新过 `updated_at`）。

|---|---|---|---|
| 1 | **无下载原文端点** | UI 的 `[下载原文]` 无处可调；设计稿 §七 sketch 早就写了这个按钮，但 P0-7-A/B 没实现 | 新增 `GET /projects/{pid}/documents/{did}/download` → `FileResponse`（带 `Content-Disposition`）|
| 2 | 列表接口不返回 `parsed_content` | 列表要显示"32 页 · 1.8 万字"，当前只有详情接口有 | 二选一：① 列表加轻量字段（page_count/char_count，不返回 markdown）；② 前端只显示状态+大小，不显示页数。**推荐 ①**（列表页信息价值高，且不传大字段）|

**决策 ① 的诚实说明**：给列表加 3 个标量字段（`page_count` / `markdown_chars` / `parse_elapsed_sec`），
**不**在列表返回 markdown（避免列表响应膨胀）。实现上从 `parsed_content` JSONB 取键。

## 九、错误处理

| 场景 | 用户提示 | 后端行为 |
|---|---|---|
| 文件 > 50MB | 对话框内红字"文件超过 50MB 限制"，不提交 | 422 `DocumentValidationError` |
| 非 PDF / 图片 | MVP **前端不拦**（后端 MinerU 会判），失败走 `failed_parse` | MinerU 抛 `Unsupported file type` |
| MinerU 解析失败 | 行内显示 `parse_error`（截断 80 字）| 状态 `failed_parse`，保留原文件 |
| PDF 加密 | 同上（错误信息来自 MinerU）| `failed_parse` |
| 队列不可用（Redis 挂）| `ElMessage.warning("解析服务暂不可用，已保存文件，请稍后点「重新解析」")` | 上传成功（201）、状态留在 `pending` |
| 后端 401/403 | Axios 拦截器统一处理（跳登录 / 提示无权）| 既有拦截器已覆盖 |
| 网络中断 | Axios 拦截器统一提示 | — |

**决策**：**前端不做 MIME 白名单**。理由：MinerU 的判断比扩展名可靠（实测把伪造的 `.pdf` 识别为 txt 并拒绝）；前端拦一道只会增加"为什么我的文件传不了"的困惑。
